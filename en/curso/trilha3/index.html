⚡ Development automations

Events that trigger agents, integration with issues, repositories, and pipelines, CI failure fixes, dependency updates, incident analysis, and documentation.

What it is:

Real process events that can trigger automatic work: approved issue, CI failure, vulnerable dependency, open PR, coverage drop, API change, incident, production error.

Why learn:

Automation without a clear event becomes a bot running for no reason. The trigger defines the value: the more predictable the event, the more reliable the automation.

Key concepts:

Event → classification → agent → validation → decision → delivery · Not every event is worth automating.

What it is:

Connect the agent to the tools where the work happens—issue tracker, repository, CI/CD—instead of creating a parallel workflow in some chat.

Why learn:

Automation that lives outside the team’s workflow dies in two weeks. Inside the PR, it’s seen, reviewed, and held accountable.

Key concepts:

The PR is the review surface · Event→change traceability · The agent has its own identity in the systems.

What it is:

A pipeline failure starts an automated investigation: the agent reads the log, reproduces the issue locally, proposes a fix, and opens a PR with evidence.

Why learn:

It’s the ideal case to start with: the trigger is objective, the verifier already exists (CI itself), and the result is reversible.

Key concepts:

Ready verifier = safe automation · Propose in a PR, never push directly · Intermittent failure requires diagnosis, not a blind retry.

What it is:

A vulnerable dependency triggers an update proposal, with the agent reading the changelog, adjusting broken code, and proving the fix with tests.

Why learn:

It’s recurring, tedious, well-defined work — exactly the kind of work that’s worth automating first.

Key concepts:

Breaking change requires reading the changelog · Updating without testing is a gamble · One dependency per PR.

What it is:

An incident triggers an automated initial diagnosis: log collection, timeline correlation, suspected recent changes, and ranked hypotheses.

Why learn:

In the first few minutes of an incident, the bottleneck is gathering information. That’s where AI helps a lot—and applying a fix on its own is where it gets in the way.

Key concepts:

Initial diagnosis is safe; mitigation in production is not · Preserve evidence before making changes · A prioritized hypothesis speeds up the human.

What it is:

The cutoff criterion: automate what is frequent, verifiable, and reversible; require approval for anything involving production, databases, infrastructure, permissions, and security.

Why learn:

Without this explicit cutoff, automation grows until it touches something nobody wanted it to touch—usually on a weekend.

Key concepts:

Not every task should be autonomous · Frequency × risk determines the level · Automation needs an owner too.

🔍 AI Code Review

Agent-assisted review: diff and repository context analysis, separation between implementer and reviewer, architectural and security review, and the limits of automated review.

What it is:

A review agent can explore related files, verify contracts, analyze tests, find duplications, and compare against repository standards—not just look at the changed lines.

Why learn:

Expensive defects are rarely in the changed line; they’re in how it interacts with the rest of the system.

Key concepts:

Diff is the starting point, not the scope · Semantic duplication only shows up in a search · The repo's conventions are a criterion.

What it is:

The recommended flow: implementation agent → deterministic tests → independent review agent → security analysis → quality gates → human review.

Why learn:

The reviewing agent shouldn’t rely on the implementer’s conclusions—the separation reduces the risk of both repeating the same incorrect assumption.

Key concepts:

Independence > capacity · Reviewer gets the spec + diff, not the author's reasoning · Clean context for each review.

What it is:

The check that the change respects module boundaries, doesn't create improper dependencies, duplicate existing capabilities, or bypass layers.

Why learn:

It’s the kind of defect no test catches and that becomes costly six months later.

Key concepts:

A boundary violation is a review finding · Semantic duplication > textual duplication · An architectural rule can become a test.

What it is:

Explicitly reviewing security failures, performance impact, and future maintenance costs—each with its own checklist.

Why learn:

A generic reviewer (“review this PR”) finds style issues. A reviewer with a defined focus finds what hurts.

Key concepts:

One lens per pass · Exposed secrets and injection are blockers, not suggestions · Maintenance is a real future cost.

What it is:

What the automated reviewer can’t see: business intent, historical context, unwritten agreements—as well as its tendency to generate large volumes of low-value comments.

Why learn:

A reviewer who comments on thirty trivial things per PR trains the team to ignore reviews — including good ones.

Key concepts:

Precision > recall in review · Findings without severity are noise · False positives cost trust.

What it is:

Human review focused on what only a human can decide: intent, priority, business risk, and acceptance of the consequences.

Why learn:

AI filters and prepares; responsibility remains with whoever approves. This isn't a formality — it's what keeps someone thinking about the problem.

Key concepts:

Responsibility cannot be delegated · Humans review intent, machines review form · A small PR is truly reviewable.

🚦 Quality Gates

The required conditions before a change can move forward: build, lint, tests, coverage, static analysis, security, compatibility, performance, and approval.

What it is:

The central principle: a rule written in text is useful; the same rule turned into an automated test is much more reliable.

Why learn:

With AI generating volume, rules that depend on someone remembering stop working during the first busy week.

Key concepts:

Gate = mandatory condition, not a recommendation · Automation > discipline · Code advances only if it passes.

What it is:

The first three gates: it compiles, follows the conventions, and unit and integration tests pass.

Why learn:

These are the gates the agent can use on its own within the loop—the faster they are, the more useful the automatic correction cycle.

Key concepts:

Slow tests don’t belong in the loop · Flaky tests destroy trust · Automatic linting eliminates style debates.

What it is:

Tests that lock down the contract with API consumers, plus a minimum coverage threshold that blocks drops.

Why learn:

As the volume of changes grows, the contract is the first silent casualty—and the customer is the one who finds out.

Key concepts:

Coverage is a floor, not a target · Preserving the contract is required · A drop in coverage blocks the merge.

What it is:

Automatic checks for critical vulnerabilities, committed secrets, dependencies with CVEs, and dangerous code patterns.

Why learn:

These are objective, high-cost findings—the perfect kind of rule to turn into an automatic block, without depending on an attentive reviewer.

Key concepts:

Never put secrets in the repository · Critical vulnerabilities block progress · Scanner noise needs calibration.

What it is:

Performance gates within an agreed limit and the requirement that every migration have a tested rollback path.

Why learn:

Degradation creeps in, one change at a time; and an irreversible migration is what turns a small mistake into a long incident.

Key concepts:

Explicit performance budget · Reversible migration is a gate · An untested rollback doesn’t exist.

What it is:

The complete pipeline: build → lint → tests → coverage → static analysis → security → review → approval → deploy. Code only moves forward when all required gates are met.

Why learn:

A gate that can be skipped “just this once” isn’t a gate—it’s a suggestion. And the exception becomes the rule in two weeks.

Key concepts:

Required means required · Exception documented with a deadline · The gate protects the team; it doesn’t get in the way.
