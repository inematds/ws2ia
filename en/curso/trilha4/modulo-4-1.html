🏚️ Safe modernization of legacy systems

AI helps a lot with understanding and converting legacy systems. But rewriting everything at once is still risky. This module is the process that replaces risk with evidence.

🗺️ Map Dependencies and Take Inventory

AI can map dependencies, explain code, document interfaces, and find dead code — reading a lot of code and summarizing its structure is where it delivers the most value. Start there: know the actual size of the problem before proposing a solution.

How to read: the entire process in one image. The cyan boxes are the evidence steps — characterize, run in parallel, compare. They turn "I think it’s the same" into proof, which is why none of them is optional.

🆕 New here?

Legacy here, it doesn’t mean "old": it means code in production that no one fully understands and that doesn’t have enough tests to be changed safely. Characterization test is a test that describes what the system does today (not what it should do). Adapter is a thin layer that translates between the old and new worlds.

🔎 Identify Hidden Business Rules

Every legacy system carries rules that were never written down anywhere: historical exceptions, special cases for large customers, rounding with a tax-related reason, deadlines inherited from a 2014 contract. These are the ones that break during a rewrite.

⚠️ Typical legacy risks

• undocumented rules
• hidden integrations
• behavior used by other systems
• outdated dependencies
• knowledge concentrated in a few people
• historical exceptions
• regulatory requirements
• manual operational processes

3

🧪 Write Characterization Tests

Characterization testing records current behavior — including what seems wrong. It does not judge; it takes a snapshot. It is the safety net that makes modernization possible.

✓ Well-done characterization

  • ✓Record the current output, even if it’s strange, with a comment: "current behavior, not validated"
  • ✓Covers real inputs collected from production (anonymized)
  • ✓Include edge cases: null, empty, negative, boundary date, maximum value
  • ✓Runs against the old system before of any change

✗ Pitfalls

  • ✗"Fix" the strange behavior while writing the test
  • ✗Test only the happy path—the legacy system lives in edge cases
  • ✗Write the expected result based on the documentation, not the execution
  • ✗Use production data without anonymizing it

💡 Practical tip

Generating characterization tests at scale is one of the best uses of AI: ask the agent to produce dozens of cases from real inputs, run them against the current system, and save the output as the expected result. You review the list instead of writing the tests one by one.

🕵️ Discover Hidden Integrations

The biggest cause of post-migration incidents is simple: you turned off something “nobody used”—and someone did. A script, a spreadsheet, a report that reads the database directly, a job owned by another team.

1

Look at access, not the code

API logs, database connections, endpoint calls, file reads. Consumers show up in the traffic, not the repository.

2

Observe for one full cycle

One week isn’t enough if there’s a monthly close, quarterly report, or annual routine. The most dangerous consumer is the one that only shows up on the 1st.

3

Turn it off in stages

Notify → deprecate (with a warning on every use) → degrade → remove. Each step gives someone a chance to show up and say, “That’s mine.”

🧱 Isolate Boundaries and Create Adapters

Before changing anything, create the seam: an interface between the consumer and the implementation. With the adapter in place, you can swap the engine without touching the driver—and roll back with one line.

📐 How to choose the right boundary

  • •Few consumers (you can notify everyone).
  • •Narrow contract: few operations, simple data.
  • •Behavior already covered by characterization tests.
  • •Clear value in migrating first (known pain, not just “it’s ugly”).

⚠️ Attention

Without a defined boundary, the migration becomes a rewrite: each piece pulls in another, the scope explodes, and the project ends up in that state where the new system isn’t ready and the old one is no longer maintained. That’s the worst possible place.

⚖️ Run in parallel and compare

Both implementations receive the same input; the old one keeps responding; the new one only logs what it would respond. Every discrepancy becomes a case to investigate. This is the strongest proof there is.

How to read: 99,84% similarity is not approval — the 241 discrepancies are the actual content of the report. Each one is a rule the characterization tests missed. That’s why you run it in shadow mode before switching over.
