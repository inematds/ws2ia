🧭 Where AI Really Fits in Engineering

The three phases (autocomplete, assistant, agent), what an agent needs to work, the engineer’s new role, and the tools’ real limitations.

What it is:

Three stages of AI use in development. Phase 1 suggests lines as you type. Phase 2 answers questions, explains, and generates files on request. Phase 3 receives a task and executes it: reads the repository, edits files, runs commands and tests, analyzes errors, and tries to fix its own implementation.

Why learn:

Each phase requires a different kind of control. Applying phase 1 habits to a phase 3 agent is the source of most accidents: you’re reviewing one line while it has already changed eighteen files.

Key concepts:

Autocomplete = suggestion · Assistant = on-demand response · Agent = execution with tools · Human responsibility shifts from the line to the system.

What it is:

The list of an agent’s operational prerequisites: controlled access to the repository, context, documentation, tools, execution environment, memory, state, permissions, rules, tests, completion criteria, an interruption mechanism, and action logging.

Why learn:

When an agent “doesn’t work,” an item from this list is almost always missing—the model isn’t weak. This is the fastest diagnosis there is.

Key concepts:

An agent is an operational component within a controlled system · Without a completion criterion, there is no completion · Without a record, there is no audit.

What it is:

The shift in work: less typing every line, more specifying, assembling context, setting limits, designing verification, and judging results.

Why learn:

Anyone who keeps measuring productivity by lines written becomes invisible; anyone who structures the system AI works in multiplies the entire team.

Key concepts:

Specify > type · Judging the result is a core skill · Speed without verification is accelerated risk.

What it is:

Durable engineering knowledge—architecture, testing, operating systems, networks, APIs, security, databases, and infrastructure—used to evaluate what AI produced.

Why learn:

Without fundamentals, you won’t notice broken concurrency, security failures, modeling errors, fragile dependencies, or impacts on another system—and the code still passes the tests.

Key concepts:

The more code is generated, the more valuable the ability to evaluate it becomes · Tools change; understanding of systems stays.

What it is:

What AI still gets systematically wrong: it sees only the context you provided, doesn’t know unwritten rules, assumes how integrations behave when it can’t observe them, and confuses “test passed” with “intent fulfilled.”

Why learn:

Knowing where the tool fails is what determines which tasks you delegate today and which require human approval.

Key concepts:

Missing context = assumption · Passing the test ≠ being correct · A known limit becomes a rule, not a surprise.

What it is:

The way of working where the only input is the sentence of the moment: no specification, no tests, no limits, and no independent review.

Why learn:

It seems productive for a week, then costs you the following month: semantic duplication, inconsistencies between modules, and changes no one can review.

Key concepts:

AI speeds up production and speeds up errors too · The differentiator isn't the prompt; it's the system around it.

📐 Spec-Driven Development

How to turn intent into a structured specification that reduces ambiguity—and that an agent can execute and verify.

What it is:

A workflow where the specification comes before the code: intent → structured specification → plan → implementation → tests → verification.

Why learn:

The specification is the only artifact that defines what “right” means. Without it, the agent and human negotiate the definition of done along the way.

Key concepts:

Spec ≠ generic text · The goal is to reduce ambiguity · Every spec ends with a verifiable criterion.

What it is:

The standard outline: problem, objective, scope, out of scope, inputs, outputs, contracts, error conditions, constraints, acceptance criteria, tests, and definition of done.

Why learn:

Every missing field becomes a decision the agent makes on its own—usually the most generic one possible.

Key concepts:

"Out of scope" prevents reckless refactoring · "Contracts" protect API consumers · "Definition of done" ends the discussion.

What it is:

The task’s explicit boundaries, plus the list of observable conditions that prove it’s complete.

Why learn:

An agent without boundaries "improves" what wasn't requested; vague criteria return work that looks done but isn't.

Key concepts:

Acceptance criteria are verifiable, not subjective · Negative scope matters as much as positive scope.

What it is:

The part of the spec that defines formats, interfaces, and behaviors to preserve, as well as what should happen in each failure case.

Why learn:

Almost every serious production regression starts with an implicit contract that no one wrote down and the AI had no way to guess.

Key concepts:

Error conditions are requirements · Compatibility is a contract · The unhappy path needs a spec just as much as the happy path.

What it is:

The canonical pair: a one-line request versus the version that specifies payment methods, idempotency, states, webhooks, retries, logs, compatibility, sensitive data, tests, rollback, and merge blocking.

Why learn:

It’s the quickest exercise for calibrating the team: everyone immediately sees how many decisions were hidden in that short sentence.

Key concepts:

Ambiguity doesn't disappear; someone decides it · The better the spec, the lower the chance of a decision that conflicts with the system.

What it is:

The practice of translating each acceptance criterion into an automated test, closing the spec → test → implementation → verification loop.

Why learn:

A rule written in text is useful; the same rule as a test is reliable—and it’s what lets you delegate execution to the agent without losing control.

Key concepts:

A test is the executable spec · Without a test, “done” is an opinion · The verifier is what authorizes autonomy.
